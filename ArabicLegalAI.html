Arabic Legal AI Assistant

Project Overview: I collaborated in a team of five to build an Arabic legal document question-answering assistant powered by a Retrieval-Augmented Generation (RAG) architecture. The system lets users upload Arabic contracts and legal documents (PDF, DOCX, or TXT), then ask natural-language legal questions and receive grounded answers backed by the exact clauses and page numbers the answer came from — instead of a generic LLM response that could hallucinate legal detail.

My Role: I handled document preprocessing and text preparation — including PDF text extraction and section-aware chunking of legal documents — implemented the Arabic text embedding pipeline using BGE-M3, integrated it with FAISS for semantic retrieval of relevant contract sections, and contributed to the retrieval pipeline that supplies relevant contract context to the Google Gemini API for grounded answer generation.

System Overview & RAG Pipeline

What the System Does


Reading and interpreting legal contracts is slow and error-prone, especially in Arabic where legal phrasing is dense and formally structured. Our assistant lets a user upload a contract and ask questions in plain Arabic — such as the termination conditions or penalty clauses — and get an answer grounded in the actual document, with the supporting clause and page number cited alongside a similarity score, rather than a free-form guess from the model.

To keep answers trustworthy, the system never lets the language model answer from memory alone. Every question is first routed through a semantic search step over the uploaded document, and only the most relevant chunks of real contract text are passed to the LLM as context before it is allowed to respond.

My Contribution: Document Preprocessing

1. PDF Text Extraction


Arabic legal PDFs are right-to-left, and PyMuPDF's raw block order doesn't always follow natural reading order. I extracted text block-by-block per page and re-sorted the blocks top-to-bottom, right-to-left, then applied light Unicode normalization to clean up PDF artifacts (soft hyphens, zero-width characters) — while deliberately leaving Arabic diacritics and letter-form variants intact, since legal wording needs to stay precise at extraction time. Pages with little to no extractable text (likely scanned images) are flagged rather than silently dropped, so they can be routed to OCR later.
pdf_extractor.py
def _extract_page_text(page: "fitz.Page") -> str:
    """Extract a single page's text using block-sorted ordering."""
    blocks = page.get_text("blocks")  # (x0, y0, x1, y1, text, block_no, block_type)
    if not blocks:
        return ""

    # Sort blocks by vertical position first (reading top -> bottom),
    # then by horizontal position reversed (right -> left) for RTL layout.
    blocks = sorted(blocks, key=lambda b: (round(b[1], 1), -b[0]))

    parts = [b[4] for b in blocks if b[4] and b[4].strip()]
    return "\n".join(parts)


def extract_pdf_text(pdf_path: str | Path) -> list[PageText]:
    """Extract text from every page of a PDF, already normalized.
    Empty/near-empty pages (e.g. scanned images with no text layer) are
    still returned so callers can detect and flag them for OCR."""
    pages: list[PageText] = []
    with fitz.open(pdf_path) as doc:
        for i, page in enumerate(doc, start=1):
            raw = _extract_page_text(page)
            clean = _normalize_arabic(raw)
            pages.append(PageText(page_number=i, text=clean))
    return pages

2. Section-Aware Chunking


Naively splitting a legal document every N words risks cutting a clause in half, which would give the retriever a chunk that's missing exactly the sentence a question is asking about. I built a sentence-safe chunker that first splits text on Arabic legal section markers (المادة / الفصل / الباب / البند — "Article" / "Chapter" / "Section" / "Clause"), then packs sentences into ~220-word windows with a sliding overlap between consecutive chunks, so context isn't lost at chunk boundaries. Every chunk keeps track of which source page(s) it came from, so answers can later cite exact page numbers.
text_chunker.py
# Legal documents are often structured in numbered articles (المادة 1 / الفصل 2).
# We try to keep article boundaries as strong split hints when present.
_ARTICLE_HINT_RE = re.compile(r"(?=(?:المادة|الفصل|الباب|البند)\s*[\d٠-٩]+)")

def chunk_document(

    doc_id: str,

    Sentences are packed into ~chunk_size_words windows, sliding back by
    overlap_words so context isn't lost at chunk boundaries."""

    for page in pages:
        for sent in _split_sentences(page.text):
            tagged_sentences.append((sent, page.page_number))

    chunks: list[Chunk] = []
    current_words: list[str] = []
    current_pages: set[int] = set()
    # ... pack sentences into windows, flushing a Chunk() once the
    # word budget is hit, then retaining the last `overlap_words`
    # words to seed the next window.
    return chunks

My Contribution: Embeddings & Semantic Retrieval

3. Arabic Embeddings with BGE-M3


For turning contract chunks into vectors, I used BAAI/bge-m3, a multilingual embedding model with strong native Arabic support. Every chunk (and every query) is encoded into a 1024-dimension dense vector, which I L2-normalize so that FAISS's inner-product search behaves as cosine similarity — keeping the retrieval math simple and fast without sacrificing accuracy.
embedder.py
def embed_texts(texts: list[str], batch_size: int = EMBED_BATCH_SIZE) -> np.ndarray:
    """Embed a list of texts (chunks or a single query) into dense vectors.
    Returns an (N, EMBED_DIM) float32 array, L2-normalized so that inner
    product search in FAISS is equivalent to cosine similarity."""
    model = get_embedder()  # lazily-loaded BGE-M3 singleton
    output = model.encode(
        texts,
        batch_size=batch_size,
        max_length=EMBED_MAX_LENGTH,
        return_dense=True,
        return_sparse=False,
        return_colbert_vecs=False,
    )
    dense = np.asarray(output["dense_vecs"], dtype="float32")

    # normalize to unit length for cosine-via-inner-product search
    norms = np.linalg.norm(dense, axis=1, keepdims=True)
    norms[norms == 0] = 1e-12
    dense = dense / norms
    return dense

4. Semantic Retrieval with FAISS


I integrated the BGE-M3 embeddings with a FAISS index to power semantic retrieval of the most relevant contract sections for a given question. The retriever validates that the FAISS index and the row-aligned chunk metadata are in sync before ever answering a query, embeds the incoming question the same way the chunks were embedded, and returns the top-K most similar chunks along with their similarity score, chunk ID, and source page numbers — the pieces of evidence that get displayed alongside the final answer.
retriever.py
def retrieve(self, query: str, top_k: int = TOP_K) -> list[dict]:
    """Retrieve the most relevant legal chunks for a query."""
    k = min(top_k, self.index.ntotal)

    # BGE-M3 returns a normalized vector with shape (1, 1024).
    query_embedding = embed_query(query)

    # Because both document and query embeddings are L2-normalized,
    # IndexFlatIP gives cosine similarity.
    scores, indices = self.index.search(query_embedding, k)

    results: list[dict] = []
    for rank, (score, index_id) in enumerate(zip(scores[0], indices[0]), start=1):
        if index_id < 0:  # FAISS returns -1 when no valid result exists
            continue
        record = dict(self.metadata[index_id])
        results.append({"rank": rank, "score": float(score), **record})

    return results

Grounded Answer Generation

Feeding Retrieved Context to Gemini


Once the top-K relevant chunks come back from the retriever, I contributed to the pipeline that structures them into a grounded legal prompt for the Google Gemini API — the retrieved contract text is injected as evidence the model must base its answer on, rather than letting it answer from general knowledge. This keeps the assistant's answers traceable back to the actual clause and page they came from, which matters a lot for legal use cases where a plausible-sounding but wrong answer is worse than no answer.

The final assistant also supports a "Full Contract Risk Audit" mode that automatically pulls out contract parties, financial obligations, penalty clauses, and liability limitations in one pass, and ships with an interactive Arabic (RTL) Streamlit interface for uploading contracts and chatting with them.
